# Task: 002 — S3 Buckets (Video Replays, Robot Models, Site Packs)

## Summary

Provision the three S3 buckets the simulation engine depends on: `video-replays` (MP4 output from the test harness, task 009/010), `robot-models` (cached MuJoCo Menagerie assets, written by task 005's robot model loader), and `site-packs` (versioned customer-specific scenario/config bundles, per the "Extensibility" principle in README.md — new customer = new pack, zero engine changes). Reference: README.md "Hard Constraints" and "Extensibility"; CLAUDE.md Stack section.

## Requirements

### video-replays bucket

1. The bucket MUST use `blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL`.
2. The bucket SHOULD have a lifecycle rule transitioning objects older than 90 days to `INFREQUENT_ACCESS` storage class.
3. Objects MUST be stored under key prefix `{scenarioId}/{runId}/replay.mp4` — document this convention in the CDK stack comments and in the spec update.

### robot-models bucket

4. The bucket MUST use `blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL`.
5. The bucket MUST use versioning (`versioned: true`) so cached model files can be rolled back if a Menagerie asset changes upstream.
6. Objects MUST be stored under key prefix `{modelName}/{version}/model.mjcf` (e.g. `unitree_g1/1.0.0/model.mjcf`).

### site-packs bucket

7. The bucket MUST use `blockPublicAccess: s3.BlockPublicAccess.BLOCK_ALL`.
8. The bucket MUST use versioning (`versioned: true`) — site packs are the customer-specific extension mechanism and MUST be individually versioned and rollback-able.
9. Objects MUST be stored under key prefix `{customerId}/{packVersion}/`.

### Shared

10. All three buckets MUST use `RemovalPolicy.DESTROY` for dev context; prod MUST use `RemovalPolicy.RETAIN`.
11. The stack MUST export all three bucket names and ARNs via `CfnOutput` following the `{ProjectName}{Resource}{Type}` naming convention.

## Technical Notes

- Add these buckets to the same data stack from task 001 (`infra/lib/robot-sim-data-stack.ts`) under a `DATA LAYER` section, OR create a sibling stack `infra/lib/robot-sim-storage-stack.ts` if task 001 is already merged and its stack is considered "closed" — check the current state of `infra/lib/` before deciding. Prefer extending the existing data stack if it exists and is uncommitted/small; keep DynamoDB and S3 in one "data layer" stack for this project's scale.
- No CORS configuration is needed on any of these buckets — access is exclusively via Lambda (server-side SDK calls) and signed URLs generated by the Lambda handler, never direct browser uploads.
